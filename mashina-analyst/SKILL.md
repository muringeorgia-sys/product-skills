# Продуктовый аналитик Mashina.kg: инсайты в .md

Перед работой прочитай целиком `lore.md` и `references/sources.md`. Остальное — на нужном шаге.

| Файл | Когда |
|---|---|
| `references/sources.md` | Шаги 2–3: доступы, дашборды, ловушки |
| `_БАЗА/Дерево-метрик.md` (проект) | Шаг 1: куда раскладывать метрику |
| `_БАЗА/Правило_Расчёт-выручки-как-в-финотчёте.md` (проект) | Любая выручка |
| `references/report-template.md` | Шаг 5: структура отчёта |
| `references/review-checklist.md` | Шаг 6: самопроверка |

## Вход

Одно из:
- вопрос PO («почему упала выручка промо», «как работает кредит на вебе»);
- фича или релиз (ключ Jira, PRD) — эффект после запуска;
- без темы («найди инсайты») — регулярный обзор за прошлую полную неделю.

## Режим «Финотчёт → таблица плана»

Вход: скриншот «Отчёт по выручке» и дата, на которую он актуален («на 18.10.2026»).

1. Прочитай скриншот: блок «Mashina», колонки «Факт», «Прогноз», «План». Даты нет — спроси.
2. Открой таблицу плана в Comet, сверь шапку: колонки текущего месяца.
3. Внеси по `references/sources.md`, раздел 5а: «Факт» и «Прогноз» строк 5–12, дату в `A1`.
4. Проверь итоги по разделу 5а. Расхождение — найди причину, не оставляй.
5. Допиши строку в `references/sources.md`, раздел 7: дата отчёта, факт, прогноз, план.
6. В чат: таблица «Было → Стало» по итогу и строкам с изменением прогноза ≥ 10%, плюс 1–2 строки: где месяц отстаёт от плана сильнее всего.

Отчёт .md в этом режиме не пишешь, если PO не попросил инсайты.

## Режим «Пуши»

Вход: «как сработали пуши», месяц или список пушей. По `references/sources.md`, раздел 5б:

1. Из листа «Пуши Mashina» возьми отправленные пуши: дата, заголовок, линия выручки, campaign_id.
2. Запусти 524 по всем id, 531 — по каждому id с выручкой. Id нет в кэше 626 — обнови 626 и повтори; не появился — в список «не попали».
3. Отметь кампании, у которых окно 7d не закрыто.
4. Сравни кампании: открытие, конверсия в трату, выручка получателей на 1 000 получателей. Сравнивай внутри одной аудитории и линии выручки.
5. Проверь, совпала ли линия выручки пуша с категорией трат из 531.
6. Отчёт по шаблону: `Инсайты_Пуши-<месяц>_<дата>.md`. Инсайт = какой тип пуша и аудитория дают трату, что повторить, что убрать из плана пушей.

Помни: выручка получателей ≠ выручка от пуша, контрольной группы нет.

## Шаги

### 1. Вопрос и рамка

Запиши для себя (в файл пока не пиши):
- какое решение примет PO по итогу;
- главная метрика и её место в дереве метрик;
- период и база сравнения: неделя к неделе, месяц к месяцу, до и после релиза. По умолчанию — последняя полная неделя пн–вс к предыдущей;
- срезы, которые нужны.

Неясно решение или период и разумного допущения нет — до 3 вопросов через AskUserQuestion. Иначе допущение пишешь в отчёт.

**Регулярный обзор без темы:** выручка в целом и по линиям → платящие и средний чек → новые и активные объявления → аудитория по платформам → воронки кредита и пополнения → установки и ретеншн приложения. Инсайт берёшь там, где изменение ≥ 10% или ≥ 5% от плана месяца.

### 2. Сбор данных

1. Redash — сначала, через API. Ищешь готовый запрос на дашборде из `sources.md`. Нет — ad-hoc SELECT.
2. GA4, Looker Studio, Adjust — через Comet по правилам `sources.md`, раздел 6.
3. Сырые выгрузки сохраняешь в `tmp/analyst_<ГГГГ-ММ-ДД>/` проекта. В отчёт они не идут.
4. По каждому числу записываешь: источник (дашборд и запрос / отчёт GA4 / дашборд Adjust), период, дата выгрузки.

Тяжёлый сбор (больше ~10 минут или больше 20 запросов) — сначала оценка и вопрос PO.

### 3. Проверка данных

До выводов:
- неполный день или неделя, часовой пояс (Redash UTC, GA4 — время property);
- релизы и изменения разметки в периоде;
- боты в GA4 (только Кыргызстан);
- задержка Adjust по iOS — последние 3 дня неполные;
- сверка выручки с финотчётом, если он есть. Расхождение — найти причину.

Нашёл поломку данных — это тоже инсайт: «данным нельзя верить, потому что…».

### 4. Анализ

1. Считаешь изменение главной метрики: число и процент.
2. Раскладываешь по дереву: какой множитель дал изменение.
3. Режешь по срезам из `lore.md` раздел 3, пока один срез не объяснит ≥ 70%.
4. Ищешь механизм: релиз, цена, сезон, канал, поломка, конкурент.
5. Подтверждаешь вторым источником.
6. Переводишь в деньги: влияние на выручку месяца и на план.
7. Формулируешь действие, владельца, срок и как проверить эффект.

Гипотезы, которые не удалось проверить, пишешь отдельно с тем, каких данных не хватает.

### 5. Отчёт

Файл: `<текущая спринт-папка>/Инсайты_<Тема>_<ГГГГ-ММ-ДД>.md`. Спринт-папка — `S..` с диапазоном, в который попадает сегодняшняя дата. Структура — `references/report-template.md`.

- 3–7 инсайтов, по убыванию денег.
- Таблицы без длинных строк: списки через `<br>`, ячейки короткие.
- Схемы — только скилл `archify` (PNG + HTML). Графики — скилл `dataviz`, PNG рядом с отчётом.

### 6. Самопроверка

Пройди `references/review-checklist.md`. Пункт не проходит — исправь.

### 7. Сдача

- В чат: ссылка на отчёт и 1–2 строки — главный инсайт с деньгами.
- Новое о источнике данных — допиши в `references/sources.md`, раздел 7.
- Дыры в разметке — список в отчёте, раздел «Чего не хватает в данных»; предложи PO запустить `analytics-spec`.
- Задача нетривиальная — короткий лог `05_logs/ГГГГ-ММ-ДД_insights_<тема>.md` и строка в `_ВИКИ/index.md` + `_ВИКИ/log.md`.
