# Приёмка релиза глазами PO

Цель — до QA-отчёта и жалоб увидеть, где прод расходится с PRD. Только чтение: прод, Jira, документы. Ничего не нажимать, что меняет данные (оплата, удаление, отправка, модерация).

## 1. Фичи релиза

- Вход — дата релиза (`ДД.ММ.ГГГГ`) или пути к PRD.
- По дате: эпики Jira с этим fixVersion (статус, ссылка на PRD) и локальные PRD с этим релизом — поиск по базе документов из правил проекта.
- Эпик не «Готово» — в отчёт строкой «не вышел», критерии не проверяй.

## 2. Чек-лист

```powershell
node ~/.claude/skills/release-check/scripts/criteria.mjs <PRD.md> [...] > <папка релиза>/Приёмка-релиза-<ДД.ММ>.md
```

Скрипт берёт раздел 6 «Критерии приёмки» и ставит тип: `сайт`, `приложение`, `админка`, `аналитика`, `QA`, `позже`.

## 3. Проверка

| Тип | Кто и как |
|---|---|
| сайт | Сначала без входа: публичная страница, HTML и данные страницы (fetch или bb-browser). Вход нужен — сессия PO в bb-browser, только чтение. Много проверок — агент `prd-site-researcher` (Sonnet) |
| приложение | Эмулятор Android по `site-mobile-researcher`; нет сборки — «не проверено» |
| аналитика | Redash или DebugView GA4, если событие уже должно идти; иначе — QA |
| админка, QA | Не проверять самому: строка в список вопросов QA |
| позже | Дата проверки в отчёт |

- Каждая проверка — итог `ок` / `расхождение` / `не проверено` и доказательство: скриншот, кусок HTML, ответ API.
- Личные данные (телефоны, имена, email) в отчёте маскировать.

## 4. Отчёт

В том же файле, сверху:
1. Одна строка: сколько критериев проверено, сколько расхождений.
2. **Расхождения** — таблица: фича, критерий, ожидалось, на проде, доказательство, что делать (баг в Jira / уточнить у QA / правка PRD).
3. **Вопросы QA** — список.
4. **Проверить позже** — с датами.

В чат — ссылка и 1–2 строки. Баги в Jira не заводить без «да» пользователя.
