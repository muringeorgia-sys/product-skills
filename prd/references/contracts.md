# Контракты: папка фичи, brief и артефакты

Один файл - один автор. Агент пишет только свой файл и не правит чужие. Язык - русский, обычный деловой, без сжатого стиля. Факты - только из источников; чего нет - «Не найдено». Таблицы уравновешены по ширине: длинные списки внутри ячейки - через `<br>`. Mermaid не используется.

## Папка фичи

```
<спринт>/<Фича>.md                     PRD
<спринт>/<Фича>_материалы/
  brief.md                             Orchestrator
  run_log.md                           Orchestrator
  research_current.md                  Site Researcher, Mashina.kg
  research_benchmark.md                Site Researcher, бенчмарк
  research_brief.md                    склейка двух файлов выше
  evidence/                            скриншоты исследователей, экраны дизайнера
  options_sketches.md                  Product Designer, стоп-точка
  metrics_and_hypotheses.md            Product Analyst
  solution_options.md                  Core PM, проход 1
  section_4.md                         Product Designer
  section_5.md                         Product Analyst, проход 2
  copy_deck.md                         UX Writer
  section_text.md                      UX Writer, приложение «Текст»
  wireframes.md                        Product Designer
  review_comments.md                   PRD Reviewer
```

## Ответ агента оркестратору

Путь к файлу, статус (`готово`, `частично`, `блокер`) и до 10 строк итога. Содержимое файла в ответ не копируется.

## brief.md - до 300 слов

```markdown
# Brief: <фича>
- Задача: <что меняем и зачем, 2-3 предложения>
- Экран и платформы: <...>
- Роли и тарифы: <покупатель / продавец / наблюдатель; частник / дилер>
- Бенчмарк: <сайт и страница> | нет
- Роль бенчмарка: образец, повторяем почти целиком | источник отдельных приёмов | только сравнение
- Масштаб изменений: точечная правка | заметная переработка | новый экран с нуля
- Мобильный образец: мобильный сайт | приложение бенчмарка | нет
- Эпик Jira (mclassified.atlassian.net): <ключ> | создать новый · Релиз: <ДД.ММ.ГГГГ> | ближайший
- Режим: Lite | Full; состав агентов: <...>
- Готовые материалы: <пути>
- Ограничения и разрешения: <что нельзя; что разрешено пользователем>
- Папка материалов: <абсолютный путь>
- PRD: <абсолютный путь>
```

| ID | Блок | Назначение | Тексты и CTA дословно | OBS |

Только наблюдения. Решения и оценки исследователь не пишет.

Склейка: `research_current.md`, затем `research_benchmark.md`. Собирает оркестратор командой `cat`, без модели.

# Метрики и гипотезы: <экран>

## PRD

Шаблон и лимиты - `prd-template.md`. В проходе 2 Core PM пишет разделы 1, 2, 3, 6; в разделе 4 оставляет строку `<!-- SECTION_4 -->`, в разделе 5 - `<!-- SECTION_5 -->`. Скрипт сборки вставляет раздел между метками `<!-- SECTION_N -->` и `<!-- /SECTION_N -->`; сборку можно повторять. Авторы разделов 4 и 5 правят только свои `section_4.md` и `section_5.md`, в PRD их не правят. В конце раздела 3 - список блоков:

```markdown
**Блоки экрана:** B1 <название> · B2 <название> · ...
```

ID блоков (B1, B2...) - общий ключ для `copy_deck.md`, `wireframes.md` и `section_4.md`.

## copy_deck.md - одна строка на элемент

```markdown
# Тексты: <фича>
| Блок | Элемент | Состояние | Текст | Лимит символов | Обоснование |
## Варианты
(только для главного заголовка и главного CTA, до 2 вариантов)
## Термины
| Термин | Как пишем | Как не пишем |
```

## section_text.md

Приложение «Текст» для PRD: таблицы по экранам по правилам `prd-template.md`, без заголовка приложения. Сборка вставляет файл между метками `<!-- SECTION_TEXT -->` и `<!-- /SECTION_TEXT -->` после раздела 6. В Lite файла нет: приложение пишет Core PM прямо в PRD.

## wireframes.md и section_4.md

Визуал - экран средней детализации: раскладка, размеры, скругления и тексты как в реальном дизайне, без цвета и проработанного UI. Правила - `roles/product-designer.md`.

```markdown
# Раскладка: <фича>
## Desktop
![desktop](evidence/wireframe_desktop.png)
## Mobile
![mobile](evidence/wireframe_mobile.png)
## Блоки
| ID | Блок | Приоритет | Содержимое | Состояния | Источник паттерна (OBS, ID блока бенчмарка) |
## Первый экран
## Поведение
```

`section_4.md` - то, что вставляется в раздел 4 PRD: картинка экрана средней детализации или схема по правилам `visualization.md`, без заголовка раздела.

## options_sketches.md

Для стоп-точки: по каждому направлению - экраны средней детализации mobile и desktop (`evidence/option_<A|B|C>_<mobile|desktop>.png`) и 3-5 строк «что меняется для пользователя».

## section_5.md

Две таблицы по правилам `analytics-rules.md`, без заголовка раздела.
