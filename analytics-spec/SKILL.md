# ТЗ на разметку

Документ для разработчиков (клиент и бэкенд) и аналитика. По нему размечают события, проверяют разметку в DebugView и собирают дашборды. Эталон - `references/example.md` (разметка пушей и отчётов по VIN/госномеру, MASHINA-250). Перед написанием прочитай его.

## Главные правила

- **Сначала задача, потом события.** Каждое событие и параметр нужны хотя бы одной метрике из раздела 7. Событие без метрики - удалить. Метрика без событий - дописать события.
- **Сухо и по делу.** Только то, что влияет на реализацию или расчёт. Обоснования решений - в чат, не в документ. Без названий методов SDK, без раздела про нейминг, без маркетингового тона.
- **Единый язык.** Термины, имена событий, параметров, таблиц, кодов ошибок - как есть латиницей. Текст - на языке пользователя. Дефис вместо тире.
- **Пробелы не выдумывать.** Чего нет во входе - `Допущение: <...>` в разделе 6, одной строкой.
- **Сверка с общим ТЗ.** Если есть «ТЗ разметки аналитики Mashina.kg» или другой tracking plan - существующие события и параметры не переименовывать, общие параметры (`platform`, `user_id`, `page_type`, `app_version`) и нотацию метрик брать оттуда ссылкой на раздел.

## Процесс

### 1. Собрать вход

Прочитай всё, что дал пользователь: PRD, тикет Jira, страницу Confluence (экспорт `.doc` - это MIME с quoted-printable HTML, декодируй), макеты, код. Если в проекте есть общее ТЗ разметки или предыдущие ТЗ - сверь имена.

Выпиши для себя: какой бизнес-вопрос закрывает разметка, воронку шагов пользователя, сущности со справочниками (типы отчётов, тарифы, категории), серверные таблицы (логи отправки, заказы), платформы.

### 2. Задать до 3 вопросов - только если без них ТЗ будет пустым

Одним `AskUserQuestion`. Приоритет:
1. Какой вопрос бизнеса должна закрыть разметка (что хотим увидеть на дашборде).
2. Где источник правды для денег и доставки: клиент или бэкенд.
3. Платформы: сайт, iOS, Android.

Остальное - допущениями.

### 3. Написать по шаблону

9 разделов, порядок фиксированный. Раздел 2 можно пропустить, если справочника нет; тогда перенумеруй разделы подряд.

**1. Задача разметки.** Один абзац: что по каждому объекту (рассылка, отчёт, объявление) видим на каждом шаге воронки - объём, конверсии, деньги. Формулировка «По каждому <объекту> видеть, <шаги воронки>, и <итог в деньгах>. Отдельно - <второй вопрос>.»

**2. Справочники.** Таблица значений enum-параметра, от которого режутся метрики: код латиницей, название, к каким сценариям относится, цена или другой атрибут. Строка правила: «Новый <объект> - новое значение в справочнике, события те же». Если метрики считаются по паре ключей - сказать прямо.

**3. Показатели.** Таблица `Показатель | Определение`. Словарь терминов, которые используются в метриках: что именно считается «тапом», «проверкой», «покупкой из пуша». Каждое определение - наблюдаемое условие (статус, таблица, событие), без «пользователь заинтересовался».

**4. События.** Таблица `Событие | Триггер | Платформы | Кто шлёт | Параметры`, в порядке воронки.
- Имя - `object_action_past`, `snake_case`. Стандартные имена GA4 (`begin_checkout`, `purchase`) не переименовывать.
- Триггер - точный момент срабатывания, наблюдаемый: «Пришёл ответ API на введённый VIN», а не «пользователь проверил авто».
- Платформы: `ios, android`, `web` или `все`.
- Кто шлёт: `клиент` / `бэкенд`. Деньги (`purchase`) и технические факты отправки - бэкенд.
- Параметры - только имена через запятую.
- Под таблицей строка про общие параметры со ссылкой на общее ТЗ и значение `page_type` для новых экранов.

**5. Параметры.** Таблица `Параметр | Тип | Обязательный | Значения`.
- Каждый параметр из раздела 4 есть здесь, лишних нет.
- Тип: `string`, `integer`, `number`. Массивов и `boolean` нет (GA4): список - строкой через запятую, флаг - enum.
- Обязательный: `да` или условие («при send_status ≠ accepted», «в сессии после тапа по пушу»).
- Значения: enum латиницей через ` / ` с пояснением, формат, пример. Деньги - число, валюта отдельным параметром. Тестовые значения помечать (`ID + _test`).

**6. Правила.** Короткие абзацы, по одному правилу в каждом:
- Атрибуция: откуда приходит ключ (data пуша, UTM, deeplink), сколько живёт (до конца сессии), что его перезаписывает, на какие события протягивается. GA4 не джойнит по ключу - разрезы передаются в каждое следующее событие.
- Признак конверсии из источника - какой параметр на `purchase` его обозначает.
- Серверные события: какой ID связывает с клиентом (`app_instance_id`, `client_id`), кто и когда его передаёт в API, где бэкенд его хранит, отправка через Measurement Protocol.
- Связки таблиц и событий: по какому ключу.
- Дедупликация: одно событие на какой ключ.
- PII: телефон, email, ФИО, VIN, госномер в аналитику не передаются.
- Регистрация в GA4: какие параметры - пользовательские измерения, какие только в BigQuery (высокая кардинальность: ID, списки).
- Ограничения GA4: ≤ 25 параметров на событие, значение ≤ 100 символов, имя ≤ 40.
- `Допущение: <...>` - каждое отдельной строкой.

**7. Метрики.** Нотация - ссылкой на общее ТЗ, плюс новые функции (например `devices(e) = uniq(app_instance_id, e)`) и уровень, на котором считаем (устройство / пользователь / сессия) с причиной одной фразой.
- Таблица `Метрика | Формула | Зачем`. Группы метрик - отдельными таблицами с вводной строкой, к чему применяется фильтр (`push_campaign_id = C`, пара `report_type = X` и `check_type = Y`).
- Формула - через события, параметры и таблицы: `count(e where p = v)`, `devices(e) / devices(e)`, `sum(value, purchase where ...)`, `строк push_log where ...`. Без словесных «примерно».
- Зачем - какое решение принимаем по метрике, 2-6 слов. Порог, если есть.
- Порядок: техника - вовлечение - воронка - деньги - отложенный эффект.
- Под таблицами: где считается (GA4 / BigQuery / Redash) и строка «Разрезы обязательны по: ...».

**8. Приёмка.** Таблица `# | Проверка | Ожидаемый результат`, 6-10 строк. Каждая проверка - действие тестировщика и что видно в DebugView / BigQuery: какие события, в каком порядке, с какими значениями. Обязательно покрыть: основной путь, повторы и дедупликацию, каждое значение справочника, веб-платформу, серверное событие, отсутствие PII, исключение тестовых данных из метрик.

**9. Дашборды.** См. ниже.

### 4. Дашборды

Раздел описывает, что аналитик собирает после релиза разметки. Каждый дашборд отвечает на один вопрос из раздела 1 и строится только из метрик раздела 7 - новых формул здесь нет.

Для каждого дашборда - подзаголовок `### 9.N <Название>` и три строки:
- **Вопрос:** что решаем по дашборду, одно предложение.
- **Для кого:** роль (продакт, маркетинг, CEO) и частота просмотра.
- **Источник и фильтры:** GA4 / BigQuery / Redash, глобальные фильтры (период, платформа, рассылка), сравнение (с прошлым периодом, между рассылками).

Затем таблица отчётов `# | Отчёт | Метрики | Вид | Разрез`:
- Отчёт - название виджета.
- Метрики - названия из раздела 7 или показатели из раздела 3, ровно как там.
- Вид: `KPI-плитка`, `воронка`, `линия по дням`, `столбцы`, `таблица`, `stacked-столбцы`. Выбор: одно число с изменением - плитка; шаги с конверсией - воронка; динамика - линия; сравнение объектов - столбцы или таблица; структура - stacked.
- Разрез - по каким параметрам делится, из «Разрезы обязательны по».

Набор дашбордов по умолчанию:
1. **Обзор / итог** - KPI-плитки главных метрик (объём, конверсия в цель, выручка) с изменением к прошлому периоду и линия по дням.
2. **Воронка** - шаги от входа до покупки с конверсиями между шагами, разрез по источнику входа и платформе.
3. **Сравнение объектов** - таблица по каждому объекту разметки (рассылка, отчёт, тариф): все метрики строкой, сортировка по выручке.
4. **Техническое качество** - доставка, ошибки, дубли, доля событий без обязательных параметров; нужен, если есть серверные события или внешние провайдеры.

Дашборды без данных для расчёта не описывать. 2-4 дашборда, в каждом 3-8 отчётов.

### 5. Самопроверка перед отдачей

- Каждое событие из раздела 4 используется в формуле раздела 7.
- Каждый параметр из раздела 4 есть в разделе 5 и наоборот.
- Каждый параметр в «Разрезы обязательны» передаётся в нужные события.
- Каждая метрика раздела 7 есть хотя бы в одном отчёте раздела 9, каждая метрика раздела 9 определена в разделе 7 или 3.
- В параметрах нет VIN, госномера, телефона, email.
- Нет массивов и boolean.

### 6. Отдать результат

Сохрани `<Короткое-имя-задачи>.md` (без префикса «ТЗ_»; заголовок документа - название задачи, без «ТЗ:») в папку текущего спринта проекта, если понятно куда, иначе в scratchpad. Отправь через `SendUserFile`.

В ответе 3-4 строки: число событий и метрик, число дашбордов, допущения и открытые вопросы. Документ не пересказывать.
